# velox2 migration planner — design

Status: draft · 2026-10-23 · Go 1.27+

This is sub-project 5 of the core design (`2026-10-14-core-design.md`, table of sub-projects): the migration planner. The schema design (`2026-10-15-schema-design.md`) made the schema DSL the single source of truth for the database too; this document says how the database follows it.

velox2 has no DDL code today. The itests and the examples write `CREATE TABLE` by hand for each dialect, and `ColumnDesc.SQLType` exists but velox-gen never fills it. Old velox forked ent's `sql/schema` on Atlas. The survey of that code found these lessons:
- two table builders drifted apart;
- planning mutated a shared model, which forced a global mutex;
- the destructive-change gate (`ValidateDiff`) was never wired, and only drop column and drop index were filtered;
- there was no rename handling, no cross-process lock, and MySQL's non-transactional DDL was half-handled;
- versioned migrations were half-built: the docs promised `Schema.Diff` and `ent://schema`, which never existed, and the runner hardcoded `$1`;
- a changed long-name hash diverged from ent silently.

Its best idea was a test: after applying a plan to a real database, a second diff is empty.

The user handed the design calls to the controller (2026-10-23: finish autonomously, best long-term design over a weaker precedent). The controller's 17 decisions are binding. A decision this document refines, because the code proved it wrong or underspecified, is marked **(changed: reason)**. Every call is marked **(call)** and numbered in the Rulings at the end.

## Intent

An application changes its schema package, runs one command, and gets a reviewable SQL file that moves its database from the last migration to the new schema. The file is plain SQL in a directory the application commits. The planner refuses changes that lose data unless the author names them. The same files apply in CI, on a laptop and in production, through one runner that locks, records and checks what it applied. A database that drifted from the files is reported, never silently "fixed".

## Goals

1. **One source of truth.** The schema package decides tables, columns, types, keys, indexes, foreign keys and enum checks on all three dialects. Nobody writes `CREATE TABLE` by hand.
2. **Planning needs no database.** `velox-gen migrate diff` compares the schema with the directory's snapshot. CI and laptops plan without production access.
3. **Reviewable, deterministic SQL.** The same schema and directory give the same bytes. Every statement is one a reviewer can read.
4. **Safe by default.** Every change has a class: safe, review or destructive. Destructive changes are refused unless allowed by name, and the allowance is recorded in the file.
5. **A runner fit for production.**
   - A cross-process lock.
   - One transaction per file where the dialect allows it.
   - A dirty state where it does not, that stops the next run until a human resolves it.
   - Checksums that refuse an edited applied file.
6. **Online where the dialect allows it.** On PostgreSQL an index on an existing table is built `CONCURRENTLY`, and a foreign key or check is added `NOT VALID` and validated afterwards.
7. **Adoption.** An existing database, including one ent or old velox created, can be adopted (`baseline`) and then brought to the schema by ordinary migrations.
8. **Every dialect.** PostgreSQL 12+, MySQL 8.0.16+ and SQLite 3.35+, tested on PostgreSQL 16, MySQL 8.4 and SQLite.

## Non-goals (v1)

- Auto-migration at program start for production. `migrate.Up` is offered for applications that embed their files; it applies reviewed files, never a fresh diff.
- Down migrations. A revert is a new forward migration.
- Data migrations generated by the planner. Users hand-write SQL files; the checksums cover them.
- Views, triggers, functions, row-level security, sequences beyond identity columns, partitions.
- Go validators as SQL `CHECK`s. Only enum checks are emitted.
- Per-column collation and charset.
- Several PostgreSQL schemas beyond what `schema.TableIn` gives (which is supported).
- Atlas, or any other schema engine.

## Anti-goals

- A destructive change applied because nobody looked: a drop, a narrowing, or a `NOT NULL` that fails on existing rows.
- Guessing a rename from similar names.
- A table the schema does not name dropped, altered or reported as a drop.
- Two code paths that build a table.
- A runner that applies half a file on MySQL and then runs the next file.
- A planner that mutates the model it was given.
- A promised feature that does not exist in the code.

## Constraints

- **Dependency discipline.** The root module's dependencies stay pgx, the MySQL driver and SQLite. `migrate` adds none.
- **The core rules hold.** Nothing runs at program start. Generated code does not change for an application that never migrates, beyond the generator fixes of §15. `GeneratedCodeIsVersion4` stays 4.
- **Deterministic output.** Every list in the model, the plan and the files is sorted by a stated key.
- **velox-gen's conventions.** The subcommands live in velox-gen. Exit codes are velox-gen's: 0 success, 1 error, 2 misuse, 3 stale or drift. Errors print as `file:line: schema User: field "name": reason`.
- **Memory.** The planner holds two models and a plan, which are small. Inspection reads the catalogue tables of the named tables only.

## Design

### 1. Where it lives (call)

- **`github.com/syssam/velox2/migrate`** is a public package: the model, `Diff`, `Lint`, `Render`, the directory, `Inspect` and the runner (`Up`, `Status`, `Resolve`, `Verify`). It imports the root package for `velox.Dialect` and the standard library. It does not import `internal/gen`.
- **`internal/gen.Tables`** is the one function that turns the resolved `Graph` into a `migrate.Schema` for one dialect. velox-gen and every test use it. Nothing else builds tables.
- **`velox-gen migrate …`** is the CLI. It lives in velox-gen because it loads the schema through `internal/gen`.

Why not a plugin: the `Graph` has `OnDelete` and the foreign-key symbols, which the plugin model deliberately lacks, and plugins write only `.go`, `.graphqls` and `.proto` files and see no database.

Why one builder: old velox had two, and they drifted.

**The model is a value.** `Diff`, `Lint`, `Render` and `Inspect` never write through a `*Schema` they are given; planning copies. Tests check it by comparing deep copies taken before each call.

### 2. The model

A `Schema` is the database as one dialect sees it. Every name is the database's name, and every type is already resolved for the dialect (§4).

```go
type Schema struct {
	Dialect velox.Dialect
	Tables  []Table // sorted by (Schema, Name)
	Enums   []Enum  // PostgreSQL native enum types, sorted by (Schema, Name); empty on other dialects
}

type TableRef struct {
	Schema string // the PostgreSQL schema or MySQL database; "" for the connection's default
	Name   string
}

type Table struct {
	Schema      string
	Name        string
	Columns     []Column     // in creation order; compared by name, not by order
	PrimaryKey  []string     // column names, in key order
	Indexes     []Index      // sorted by Name
	ForeignKeys []ForeignKey // sorted by Name
	Checks      []Check      // sorted by Name
	Comment     string       // "" on SQLite
	Collation   string       // MySQL: the table's collation, "utf8mb4_bin" for planned tables; "" elsewhere
	Pos         string       // the schema's file:line, when known; never serialized or compared
}

type Column struct {
	Name     string
	Type     string // the canonical spelling for the dialect (§4)
	Nullable bool
	Default  string // the SQL of the DEFAULT clause, canonical (§5); "" for none
	Identity bool   // the database assigns the value: IDENTITY, AUTO_INCREMENT, or SQLite's rowid
	Comment  string // "" on SQLite
	Pos      string
}

type Index struct {
	Name    string
	Columns []string
	Unique  bool
	Where   string // the predicate of a partial index; "" for none; never on MySQL
	Pos     string
}

type ForeignKey struct {
	Name       string
	Columns    []string
	RefTable   TableRef
	RefColumns []string
	OnDelete   string // "", "CASCADE", "SET NULL" or "RESTRICT"; "" is NO ACTION
	Pos        string
}

type Check struct {
	Name string
	Expr string // canonical (§7)
	Pos  string
}

type Enum struct { // a PostgreSQL CREATE TYPE … AS ENUM
	Schema string
	Name   string
	Values []string // in the type's order
	Pos    string
}
```

**(changed: the decision's model gains `Pos`, `Collation`, `Enums`, `Check.Expr` and `TableRef`.)** `Pos` lets a refusal or a lint name the schema's file:line. `Collation` lets drift and baseline see a MySQL table that is not `utf8mb4_bin`. `Enums` holds the native enum types of ruling 21. `Check.Expr` keeps checks the model did not create, so a baselined database is modelled faithfully.

**Equality** (`Schema.Equal`) ignores `Pos` and column order, and compares everything else exactly, after the canonical forms of §4, §5 and §7.

**The snapshot** is the model as JSON: `schema.json` in the directory (§9). It is indented, sorted as above, and holds `"version": 1` and `"dialect"`.

### 3. From the schema to the model: `internal/gen.Tables`

`Tables(g *Graph, d velox.Dialect) (*migrate.Schema, error)` builds one table per entity and per many-to-many join table. Its errors are `*gen.Error` values with positions, joined like `Build`'s.

**Tables.** The entity's `Table` and `TableSchema` (`schema.TableIn`). The comment is the entity's `Comment` annotation. On MySQL every table has `Collation: "utf8mb4_bin"`.

**Columns.** One per `Graph` field, in the `Graph`'s order: the ID, then the declared fields, then the implicit foreign keys.
- **Type:** §4.
- **Nullable:** the one rule the plugin model and the core already agree on (§15.3). A column is NULL-able when the field is `Nillable`, or when it is an `Optional` JSON field whose Go type holds nil (a slice, a map or a pointer). Every other column is `NOT NULL`, `Optional` ones included: velox stores their zero value (API cleanup spec §3.1).
- **Default:** §5.
- **Identity:** an integer ID. velox's insert treats a zero integer key as one the database assigns (`generatedKey` in `insert.go`), so every integer ID is an identity column.
- **Comment:** the field's `Comment`. An implicit foreign key takes its edge's `Comment` (call).

**Primary key.** `[id column]`, or the join table's `[owner column, target column]`, as `lower.go` makes the join entity.

**Indexes,** sorted by name:
1. Each declared index (`Graph.Indexes`), with its name (§6).
2. Each `Unique` field that is not the ID: a unique index on that column, unless a declared unique index on that column alone exists. This is `lower.go`'s rule; the name is `indexName`'s (`<table>_<col>_unique`).
3. **Foreign-key indexes (call).** Each foreign-key column that is not the leading column of the primary key or of another index gets a non-unique index `<table>_<col>`. A join table's target column is one. Why: velox loads edges by `WHERE fk IN (…)`, and MySQL's InnoDB creates exactly such an index for any foreign key without one. Modelling it keeps `inspect == model` true on MySQL and makes loads indexed on the others.

**Foreign keys.** One per relation that holds a key (`Rel.Kind` O2M, M2O, O2O), on the table holding the column, referencing the target's ID. Its `OnDelete` is `Rel.OnDelete`. A join table has two, both `ON DELETE CASCADE` **(call)**: rule 45's message says join rows go with either end, and the database is where that holds for every writer. The names are §6's.

**A foreign-key column copies the referenced column's type (call).** It drops the identity. So a `uint64` ID, which is `bigint` on PostgreSQL (§4), gives `bigint` foreign keys, even when the key field is declared `field.Uint64`. PostgreSQL refuses a foreign key between `numeric` and `bigint`, and MySQL one between signed and unsigned columns.

**Checks.** An enum field gets `CHECK (<col> IN (<values in declaration order>))`, named `<table>_<col>_check`, on every dialect, unless the field is `Native()` on PostgreSQL or MySQL (ruling 21). A NULL-able enum passes NULL, as SQL does.

**Native enums.** On PostgreSQL a `Native()` enum field gets an `Enum` named `<table>_<col>` (capped, §6) in the table's schema, and the column's type is that name. On MySQL the column's type is `enum('a','b')`. On SQLite `Native()` changes nothing: the column keeps its `CHECK`.

**Refusals at plan time (call).** `Tables` refuses, with the element's file:line:
- **MySQL:**
  - an `Index.Where`: MySQL has no partial index (closes follow-up :333);
  - an index or unique field on a column of a `text`, `blob` or `json` type: InnoDB needs a prefix, which velox does not model; the message suggests `MaxLen` or `SchemaType`;
  - an index whose key is over 3072 bytes, counting 4 bytes per `varchar` character and the fixed size of other types;
  - a string `Default` containing a backslash, whose literal depends on the session's `NO_BACKSLASH_ESCAPES`; the message suggests `SchemaDefault`;
  - an enum value over 255 bytes (the column is `varchar(255)`);
  - a column comment over 1024 characters, or a table comment over 2048.
- **SQLite:** a `TableSchema` (`schema.TableIn`): an attached database is not a schema velox manages.
- **Any dialect:** a `field.Other` with no `SchemaType` for the dialect (rule 26 checks only that some key is set).

`Tables` runs `Build`'s rules first, so rule 44 and the rules of §15 have already passed.

### 4. Types

A column's `Type` is the canonical spelling: what the database reports when inspected, lower case. `Render` writes it verbatim, so built-in types need no mapping back. A `SchemaType` for the dialect overrides the table and is normalised by a per-dialect alias list (for PostgreSQL: `varchar`, `int4`, `int8`, `float8`, `bool`, `timestamptz`, `decimal`, `int` → their canonical forms). Any other spelling is compared after lower-casing and collapsing white space. `SchemaType`'s doc says to write it as the database prints it.

`Size` comes from `MaxLen` (strings and bytes) or `Text` (`math.MaxInt32`). It counts bytes.

| Field type | PostgreSQL | MySQL | SQLite |
|---|---|---|---|
| `bool` | `boolean` | `tinyint(1)` | `boolean` |
| `int8` | `smallint` | `tinyint` | `integer` |
| `int16` | `smallint` | `smallint` | `integer` |
| `int32` | `integer` | `int` | `integer` |
| `int`, `int64` | `bigint` | `bigint` | `integer` |
| `uint8` | `smallint` | `tinyint unsigned` | `integer` |
| `uint16` | `integer` | `smallint unsigned` | `integer` |
| `uint32` | `bigint` | `int unsigned` | `integer` |
| `uint`, `uint64` | `numeric(20,0)` | `bigint unsigned` | `integer` |
| `float32` | `real` | `float` | `real` |
| `float64` | `double precision` | `double` | `real` |
| `string`, Size 0 | `text` | `varchar(255)` | `text` |
| `string`, Size 1–10485760 | `character varying(Size)` | Size ≤ 16383: `varchar(Size)`; ≤ 65535: `text`; ≤ 16777215: `mediumtext`; else `longtext` | `text` |
| `string`, larger (`Text`) | `text` | `longtext` | `text` |
| `enum` | `text` | `varchar(255)` | `text` |
| `enum`, `Native()` | `"<table>_<col>"` (a `CREATE TYPE`) | `enum('a','b',…)` | `text` |
| `bytes`, Size 0 | `bytea` | `blob` | `blob` |
| `bytes`, Size 1–255 | `bytea` | `varbinary(Size)` | `blob` |
| `bytes`, larger | `bytea` | ≤ 65535: `blob`; ≤ 16777215: `mediumblob`; else `longblob` | `blob` |
| `time` | `timestamp with time zone` | `datetime(6)` | `datetime` |
| `uuid` | `uuid` | `char(36)` | `text` |
| `json` | `jsonb` | `json` | `text` |
| `other` | `SchemaType` | `SchemaType` | `SchemaType` |

**Integer IDs** are identity columns of their type:
- PostgreSQL: `<type> GENERATED BY DEFAULT AS IDENTITY`. A `uint`/`uint64` ID is `bigint` (call): an identity cannot be `numeric`, and its values are 1 … 2⁶³−1, which pgx binds and scans into a `uint64`.
- MySQL: `<type> AUTO_INCREMENT`.
- SQLite: `integer PRIMARY KEY AUTOINCREMENT` **(changed: the decision said `INTEGER PRIMARY KEY`, which reuses the highest rowid after its row is deleted. PostgreSQL's identity and MySQL's `AUTO_INCREMENT` never reuse an ID, and ent and old velox use `AUTOINCREMENT`. One behaviour on all three dialects is worth the `sqlite_sequence` row.)**

**Why each choice.** The itests already use these types, and the runtime binds and scans them as follows:
- **time:** `datetime(6)` keeps microseconds and has no 2038 limit, unlike `timestamp`. The MySQL DSN needs `parseTime=true`, as velox already requires. SQLite's driver reads a `datetime` column back as `time.Time`, which a `text` column would not.
- **uint64:** pgx encodes a `uint64` as `numeric` and scans `numeric` into `*uint64` (pgtype's `uint64Wrapper` has `NumericValue` and `ScanNumeric`). It refuses a value over 2⁶³−1 for `bigint`. So `numeric(20,0)` holds the whole range (call). MySQL's driver binds a `uint64` with the high bit set, and `bigint unsigned` holds it. SQLite's `integer` is a signed 64-bit integer: a value over 2⁶³−1 is out of range. An itest pins that it fails at bind and never reads back a different value, and the doc of `field.Uint64` says so.
- **uuid:** the planner assumes the type's `Valuer` binds the canonical 36-character text, as `google/uuid` and `gofrs/uuid` do. PostgreSQL's `uuid` accepts that text, and pgx scans `uuid` into a `sql.Scanner` as text. A type whose `Valuer` binds 16 bytes needs `SchemaType` (for example `binary(16)` on MySQL). An itest uses a test-local UUID type, so the module gains no dependency.
- **json:** the JSON-fields rulings (schema design §1.1) bind `[]byte` on PostgreSQL and a string on MySQL and SQLite. These are the column types they assume.
- **bool:** MySQL's `BOOLEAN` is `tinyint(1)`, which is what it reports, so the model says so **(changed: the decision wrote `boolean`; that is a spelling MySQL never reports, so `inspect == model` would fail)**.
- **strings on MySQL:** `MaxLen` counts bytes and `varchar(n)` counts characters, so `varchar(Size)` always holds the value. `varchar` stops at 16383 because utf8mb4 uses up to 4 bytes per character within the 65535-byte row limit. Beyond that the text family is chosen by bytes.
- **strings on SQLite:** always `text`. SQLite does not enforce a length, so a `MaxLen` change is no SQLite change.

**MySQL tables** are `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_bin`. Byte-wise comparison matches PostgreSQL's equality and SQLite's default.

### 5. Defaults

velox's insert writes every column but a generated key (`insertColumns`), and it fills `Default` and `DefaultFunc` in Go. So a database default never changes what velox writes. It serves two things: rows written outside velox, and existing rows when a column is added. Rule 7's "add a NOT NULL column with no default" depends on it.

A column's `Default` is:
1. the field's `SchemaDefault` for the dialect, verbatim, when there is one (§15.1);
2. else a literal `Default` of a `bool`, number, string or enum field, rendered per dialect:
   - a string is quoted with `''` doubling; on MySQL a `text`-family column takes the expression form `('…')`;
   - a bool is `true`/`false` on PostgreSQL and `1`/`0` on MySQL and SQLite;
   - a number is printed with `strconv`, the shortest form that reads back exactly;
3. **else, for an `Optional` field that is not `Nillable`, of type string, bool or number, the zero value: `''`, `false`/`0`, `0` (call).** **(changed: decision 11 gave such a field no default.)** velox stores the zero value for an unset `Optional` field, so the zero value is that column's default in fact. Declaring it makes adding an `Optional` field to an existing table safe, which is the commonest migration. A required field still gets no default, so adding it stays destructive until the author gives one.
4. else none.

A `DefaultFunc`, a time or UUID `Default`, and a JSON, bytes or other literal `Default` stay Go-side, with no database default unless `SchemaDefault` gives one (call). An `UpdateDefault` never becomes `ON UPDATE` (call).

**`mixin.Time` gains a `SchemaDefault` (call):** `now()` on PostgreSQL, `CURRENT_TIMESTAMP(6)` on MySQL and `CURRENT_TIMESTAMP` on SQLite, on both `created_at` and `updated_at`. So adding the mixin to an existing table is safe. It changes the model hash of every package that uses the mixin, which a regenerate absorbs.

**Canonical form for comparison.** `Inspect` normalises what the database reports:
- PostgreSQL's `'x'::text` and `'-1'::integer` casts are stripped from literals;
- numbers are compared as numbers;
- MySQL's `DEFAULT_GENERATED` expressions are wrapped as the model writes them.

An expression the normaliser cannot match is reported by drift with both spellings. `SchemaDefault`'s doc says to write the expression as the database prints it.

### 6. Names

- **Tables and columns** are the `Graph`'s: `Entity.Table` and `Field.Column`, join tables as `Build` derives them.
- **Primary key:** PostgreSQL `<table>_pkey` (its own default), MySQL `PRIMARY`, SQLite none. The model holds no primary-key name, and comparison ignores it.
- **Declared index:** its `StorageKey`, else `indexName`: `<table>_<cols…>`, then `_unique` for a unique index, then `_<fnv-1a 32 of Where, 8 hex>` for a partial one. This is the existing derivation in `internal/gen/build.go`.
- **Unique field:** `indexName` of a one-column unique index: `<table>_<col>_unique`.
- **Foreign-key index:** `<table>_<col>`.
- **Foreign key:** `edge.Symbol` (or, for a join table, `edge.Symbols(to, from)`, in the order of its columns), else `<table>_<col>_fkey`, PostgreSQL's own default.
- **Enum check:** `<table>_<col>_check`, PostgreSQL's own default.
- **Native enum type (PostgreSQL):** `<table>_<col>`.
- **Helpers the renderer makes:** `<table>_<col>_not_null` (the temporary check of §7.4), `velox_new_<table>` (SQLite's rebuild), `<type>_velox_old` (PostgreSQL's enum swap).

**The cap (call).** A derived name over 63 bytes becomes its first 54 bytes, cut back to a UTF-8 boundary, then `_`, then the 8 hex digits of the FNV-1a 32 hash of the whole uncapped name: 63 bytes at most. One cap on every dialect, so one schema works on all three: PostgreSQL truncates at 63, and MySQL refuses names over 64. velox-gen applies it, so the `Graph`'s index names, `describe` and the plugin model show the capped name.

**Explicit names are not capped; they are refused** (rule 50, §15.2) when over 63 bytes: tables, columns, join tables, index `StorageKey`s and `Symbol`s. **(changed: the decision capped every identifier. Capping a name the author wrote would put a name in the database that appears nowhere in the schema.)**

**One namespace per database schema (rule 44, extended).** All of these must be distinct, compared case-insensitively:
- table names;
- index names, derived (after the cap) and explicit, unique-field indexes and foreign-key indexes included;
- PostgreSQL primary-key names;
- foreign-key and check names;
- native enum type names;
- PostgreSQL identity sequences (`<table>_<col>_seq`).

The reasons: PostgreSQL puts tables, indexes and sequences in one namespace (`pg_class`), and tables and enum types in another (`pg_type`). MySQL keeps foreign-key and check names per database. MySQL's table names are case-insensitive on some platforms. A collision is refused, naming both elements and suggesting `StorageKey` or `Symbol`. This closes follow-up :271.

**ent-compatible names** (follow-up :138) are not copied. velox keeps `<table>_<cols>`. Diff matches indexes and constraints by definition (§7.1), so adopting an ent database (`baseline`, then `diff`) gives a migration of `RENAME`s, with no flag. Tables and columns need `-rename-table`/`-rename-column`. **(changed: the decision named "baseline plus the rename flag"; for indexes and constraints the flag is not needed.)**

### 7. Diff

`Diff(from, to *Schema, opts DiffOptions) ([]Change, error)` compares two models of one dialect. `from` is the snapshot (or an inspected database), and `to` is the desired model.

#### 7.1 Matching

- **Tables** match by `TableRef`. A table renamed in `opts.RenameTables` matches its new name. A table of `from` with no match is dropped, and one of `to` is created.
- **Columns** match by name within a matched table, after `opts.RenameColumns`. A change of `StorageKey` with no flag is a drop plus an add: destructive, so refused. Nothing guesses a rename (decision 8).
- **Indexes** match by name. Otherwise, an unmatched index of `from` and one of `to` with equal columns, `Unique` and `Where` are a rename (call). The same holds for foreign keys (columns, reference, `OnDelete`) and checks (`Expr`). This is exact: no data depends on the name.
- **Native enum types** match by name. Values present in `from` and in `to` must keep their relative order, or the change is a reorder.
- **The primary key** cannot change. A changed primary key is an error naming the table: write that migration by hand (call).

Renames name what they act on by its name in `from`: `RenameColumns` keys a column by its table's `from` name. A rename that names nothing in `from`, or a target that already exists in `to`, is an error.

#### 7.2 Changes

`Change` is a sealed interface; each kind is a struct.

| Change | Fields |
|---|---|
| `CreateTable` | `Table Table` |
| `DropTable` | `Table Table` (as in `from`) |
| `RenameTable` | `From, To TableRef` |
| `AddColumn` | `Table TableRef; Column Column` |
| `DropColumn` | `Table TableRef; Column Column` |
| `RenameColumn` | `Table TableRef; From, To string` |
| `AlterColumn` | `Table TableRef; From, To Column; What ColumnChange` (a bit set: type, nullable, default, identity, comment) |
| `AddIndex`, `DropIndex` | `Table TableRef; Index Index` |
| `RenameIndex` | `Table TableRef; From, To string` |
| `AddForeignKey`, `DropForeignKey` | `Table TableRef; ForeignKey ForeignKey` |
| `AddCheck`, `DropCheck` | `Table TableRef; Check Check` |
| `RenameConstraint` | `Table TableRef; From, To string` (a foreign key or a check) |
| `SetTableComment` | `Table TableRef; From, To string` |
| `CreateEnum`, `DropEnum` | `Enum Enum` |
| `AlterEnum` | `From, To Enum` (values added, or a reorder or removal) |

#### 7.3 Order

`Diff` returns the changes in this order. Within each step they are sorted by table (`Schema`, `Name`), then by object name or column position.
1. Drop the foreign keys that are dropped, that reference a dropped table, or whose columns change type. Drop the checks and indexes that are dropped or that cover a dropped column.
2. Rename tables, then columns, then indexes and constraints.
3. Create native enum types; add enum values.
4. Create tables, ordered so that a referenced table comes first. Foreign keys inside a cycle are added after all the tables.
5. Add columns; alter columns; set comments.
6. Drop columns.
7. Add indexes; add checks; add foreign keys, including the ones step 1 dropped to change a type.
8. Drop tables, children first; swap or drop native enum types no column uses any more.

### 8. Changes, lints and SQL

#### 8.1 Classes and codes

`Lint(from *Schema, changes []Change) []Finding` gives each change at most one finding of each code. A change with no finding is safe. "Existing table" means a table of `from`.

| Code | Class | When |
|---|---|---|
| `drop-table` | destructive | `DropTable` |
| `drop-column` | destructive | `DropColumn` |
| `alter-type` | destructive | a type change that is not a widening |
| `set-not-null` | destructive | NULL-able → `NOT NULL` |
| `add-required-column` | destructive | `NOT NULL`, no default, on an existing table |
| `add-unique` | destructive | a unique index on an existing table |
| `drop-enum-value` | destructive | an enum (check or native) loses a value |
| `reorder-enum` | destructive | a native enum's values change order, or MySQL gains a value anywhere but the end |
| `convert-collation` | destructive | MySQL: a table's collation changes (a rewrite that can create duplicates) |
| `rename-table`, `rename-column` | review | the old code breaks during a rolling deploy |
| `widen-type` | review | `smallint`→`integer`→`bigint`; `real`→`double precision`; `varchar(n)`→`varchar(m>n)` or `text`; the MySQL text and blob families upward |
| `add-index` | review | a non-unique index on an existing table |
| `add-foreign-key` | review | on an existing table; it fails if rows are orphaned |
| `add-check` | review | an enum check on an existing table, or one gaining a value; on MySQL it copies the table |
| `drop-index`, `drop-foreign-key`, `drop-check` | review | not part of a type change or a rebuild |
| `sqlite-rebuild` | review | a SQLite change that rebuilds the table (§8.4) |
| `volatile-default` | review | PostgreSQL: adding a column with a `SchemaDefault` expression, which rewrites the table if the expression is volatile |

`widen-type` on PostgreSQL is safe for `varchar` growth and `varchar`→`text` (no rewrite), and review otherwise (a rewrite under an exclusive lock).

**Allowing (decision 7).** `Blocked(findings, allow)` returns the destructive findings no `Allow` covers. `Allow{Code, Target}` covers one code, for one target (`users.name`, `users`) or for every target when `Target` is "". The flag form is `-allow drop-column=users.name,drop-table`. The allowed set extends the default (safe and review); it never replaces it. Each allowed finding is written into the file as a `-- velox:allow` directive. Each review finding is written as a `-- review:` comment above its statement.

#### 8.2 SQL per change

Identifiers are always quoted: `"x"` on PostgreSQL and SQLite, `` `x` `` on MySQL. Statements end with `;` in the file. Several actions on one table form one `ALTER TABLE` where the dialect allows a list (PostgreSQL, MySQL), so the lock is taken once.

**CreateTable.**
```sql
-- PostgreSQL
CREATE TABLE "users" (
  "id" bigint GENERATED BY DEFAULT AS IDENTITY,
  "org_id" bigint NOT NULL,
  "role" text NOT NULL DEFAULT 'viewer',
  CONSTRAINT "users_pkey" PRIMARY KEY ("id"),
  CONSTRAINT "users_org_id_fkey" FOREIGN KEY ("org_id") REFERENCES "orgs" ("id") ON DELETE CASCADE,
  CONSTRAINT "users_role_check" CHECK ("role" IN ('viewer', 'admin'))
);
CREATE UNIQUE INDEX "users_email_unique" ON "users" ("email");
CREATE INDEX "users_org_id" ON "users" ("org_id");
COMMENT ON TABLE "users" IS '…';   COMMENT ON COLUMN "users"."role" IS '…';

-- MySQL
CREATE TABLE `users` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `org_id` bigint NOT NULL,
  `role` varchar(255) NOT NULL DEFAULT 'viewer' COMMENT '…',
  PRIMARY KEY (`id`),
  UNIQUE INDEX `users_email_unique` (`email`),
  INDEX `users_org_id` (`org_id`),
  CONSTRAINT `users_org_id_fkey` FOREIGN KEY (`org_id`) REFERENCES `orgs` (`id`) ON DELETE CASCADE,
  CONSTRAINT `users_role_check` CHECK (`role` IN ('viewer', 'admin'))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_bin COMMENT='…';

-- SQLite
CREATE TABLE "users" (
  "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
  "org_id" integer NOT NULL,
  "role" text NOT NULL DEFAULT 'viewer',
  CONSTRAINT "users_org_id_fkey" FOREIGN KEY ("org_id") REFERENCES "orgs" ("id") ON DELETE CASCADE,
  CONSTRAINT "users_role_check" CHECK ("role" IN ('viewer', 'admin'))
);
CREATE UNIQUE INDEX "users_email_unique" ON "users" ("email");
```
- A table in a schema is qualified: `"billing"."invoices"` on PostgreSQL, `` `billing`.`invoices` `` on MySQL.
- On PostgreSQL, a schema that no table of `from` uses is created first with `CREATE SCHEMA IF NOT EXISTS` (call). On MySQL the database must exist; the planner never creates databases (call).
- A partial index is `CREATE INDEX … WHERE <Where>`.
- A unique field or index is a unique index, never a `UNIQUE` constraint (call): one kind of object, which velox's `ON CONFLICT (cols)` reads like a constraint.
- A non-integer primary key on SQLite is a table constraint, `CONSTRAINT … PRIMARY KEY ("id")`, with the column `NOT NULL` (SQLite allows NULL keys otherwise).

**Other changes.**

| Change | PostgreSQL | MySQL | SQLite |
|---|---|---|---|
| DropTable | `DROP TABLE "t"` | `DROP TABLE` `` `t` `` | `DROP TABLE "t"` |
| RenameTable | `ALTER TABLE "a" RENAME TO "b"`; a schema move adds `SET SCHEMA` | `RENAME TABLE a TO b` | `ALTER TABLE "a" RENAME TO "b"` |
| AddColumn | `ALTER TABLE t ADD COLUMN <def>` | `ALTER TABLE t ADD COLUMN <def>` | `ALTER TABLE t ADD COLUMN <def>`, or a rebuild (§8.4) |
| DropColumn | `ALTER TABLE t DROP COLUMN c` | same | `ALTER TABLE t DROP COLUMN c`, or a rebuild |
| RenameColumn | `ALTER TABLE t RENAME COLUMN a TO b` | same | same |
| AlterColumn, type | `ALTER COLUMN c TYPE x USING "c"::x` | `MODIFY COLUMN <full def>` | rebuild |
| AlterColumn, nullable | `ALTER COLUMN c DROP NOT NULL`; `SET NOT NULL` per §8.3 | `MODIFY COLUMN <full def>` | rebuild |
| AlterColumn, default | `ALTER COLUMN c SET DEFAULT x` / `DROP DEFAULT` | `ALTER COLUMN c SET DEFAULT x` / `DROP DEFAULT` | rebuild |
| AlterColumn, identity | `ALTER COLUMN c ADD GENERATED BY DEFAULT AS IDENTITY` / `DROP IDENTITY` | `MODIFY COLUMN <full def>` | rebuild |
| AlterColumn, comment | `COMMENT ON COLUMN … IS …` | `MODIFY COLUMN <full def>` | — |
| AddIndex | `CREATE [UNIQUE] INDEX …`; an existing table's goes to the online script (§8.3) | `CREATE [UNIQUE] INDEX n ON t (cols) ALGORITHM=INPLACE LOCK=NONE` | `CREATE [UNIQUE] INDEX …` |
| DropIndex | `DROP INDEX "n"` | `DROP INDEX n ON t` | `DROP INDEX "n"` |
| RenameIndex | `ALTER INDEX "a" RENAME TO "b"` | `ALTER TABLE t RENAME INDEX a TO b` | drop and create |
| AddForeignKey | `ADD CONSTRAINT n FOREIGN KEY … NOT VALID`, and `VALIDATE` online, on an existing table | `ADD CONSTRAINT n FOREIGN KEY …` | rebuild |
| DropForeignKey | `DROP CONSTRAINT n` | `DROP FOREIGN KEY n` | rebuild |
| AddCheck | `ADD CONSTRAINT n CHECK (…) NOT VALID`, and `VALIDATE` online, on an existing table | `ADD CONSTRAINT n CHECK (…)` | rebuild |
| DropCheck | `DROP CONSTRAINT n` | `DROP CHECK n` | rebuild |
| RenameConstraint | `ALTER TABLE t RENAME CONSTRAINT a TO b` | drop and add | rebuild |
| SetTableComment | `COMMENT ON TABLE t IS …` | `ALTER TABLE t COMMENT = …` | — |
| CreateEnum | `CREATE TYPE "n" AS ENUM ('a', 'b')` | — (inline type) | — |
| AlterEnum, add | `ALTER TYPE "n" ADD VALUE 'c' [BEFORE 'b']`, in its own file outside a transaction | `MODIFY COLUMN c enum(…,'c')` | the check, rebuilt |
| AlterEnum, remove or reorder | the swap below | `MODIFY COLUMN c enum(…)` | the check, rebuilt |
| DropEnum | `DROP TYPE "n"` | — | — |

- **MySQL `MODIFY COLUMN`** writes the whole definition (type, nullability, default, `AUTO_INCREMENT`, comment), as MySQL requires.
- **A type change on a key** (an ID's type) drops the foreign keys on and to the column first, and re-adds them in step 7 (§7.3), since MySQL refuses to modify a column a foreign key uses.
- **PostgreSQL's enum swap:**
  ```sql
  ALTER TYPE "n" RENAME TO "n_velox_old";
  CREATE TYPE "n" AS ENUM (…);
  ALTER TABLE t ALTER COLUMN c DROP DEFAULT, ALTER COLUMN c TYPE "n" USING "c"::text::"n", ALTER COLUMN c SET DEFAULT …;
  DROP TYPE "n_velox_old";
  ```
  The default is dropped and set again around the type change.

#### 8.3 PostgreSQL: lock timeout and the online script

Every PostgreSQL and MySQL file carries `-- velox:lock-timeout 5s` (the directory's default, `-lock-timeout` to change it). The runner sets it: `SET LOCAL lock_timeout` in a transaction, `SET lock_timeout` then `RESET` outside one, and `SET SESSION lock_wait_timeout` on MySQL. A migration waiting on a busy table then fails fast instead of queueing every query behind it. **(changed: "files set lock_timeout" becomes a directive the runner applies, so the value works in and out of a transaction and on MySQL.)**

Work that must not hold a lock for long, or cannot run in a transaction, goes to a second file, the **online script**. It has the next version, the suffix `_online` and `-- velox:no-transaction`. Each statement commits alone:
- **an index on an existing table:** `DROP INDEX CONCURRENTLY IF EXISTS "n"; CREATE [UNIQUE] INDEX CONCURRENTLY "n" ON …`. The drop makes the pair safe to repeat after a failure, which leaves an invalid index;
- **a constraint added `NOT VALID`** in the main file: `ALTER TABLE t VALIDATE CONSTRAINT n`;
- **`SET NOT NULL` on an existing column** (when allowed): the main file adds `CHECK ("c" IS NOT NULL) NOT VALID` as `<table>_<col>_not_null`. The online script validates it, runs `ALTER COLUMN c SET NOT NULL` (which PostgreSQL 12+ proves from the valid check without a scan), and drops the check;
- **native enum values added** (`ALTER TYPE … ADD VALUE`), in a file of their own that runs before the main file. A value added in a transaction cannot be used in it.

MySQL has no online script. Its `ALGORITHM=INPLACE LOCK=NONE` fails rather than locking, and every MySQL file runs outside a transaction anyway (§10). SQLite has none either: its writes lock the database.

#### 8.4 SQLite: the table rebuild

SQLite cannot alter a column's type, nullability or default, or add or drop a constraint. It also cannot add a column that is `NOT NULL` with a non-constant default, nor drop a column that a key, an index or a constraint uses. For these the renderer rebuilds the table, following SQLite's documented procedure:

```sql
-- velox:foreign-keys off
CREATE TABLE "velox_new_users" ( …the new definition… );
INSERT INTO "velox_new_users" ("id", "name", …) SELECT "id", "old_name", … FROM "users";
DELETE FROM sqlite_sequence WHERE name = 'velox_new_users';
INSERT INTO sqlite_sequence (name, seq) SELECT 'velox_new_users', seq FROM sqlite_sequence WHERE name = 'users';
DROP TABLE "users";
ALTER TABLE "velox_new_users" RENAME TO "users";
CREATE INDEX … ;   -- every index of the new table
```

- The copy lists the columns both tables have, under their new names. A new `NOT NULL` column takes its default.
- The two `sqlite_sequence` statements keep the `AUTOINCREMENT` counter, so a deleted top ID is not reused.
- Every change to one table in one plan folds into one rebuild.

**`PRAGMA foreign_keys` cannot change inside a transaction.** So the rebuild cannot turn foreign keys off "in the file's transaction", as decision 13 said **(changed: SQLite ignores the pragma inside a transaction, and with foreign keys on, the `DROP TABLE` runs each child's `ON DELETE` action, which with `CASCADE` deletes the children)**. The file carries `-- velox:foreign-keys off` instead. The runner turns foreign keys off on its connection before `BEGIN`. It runs `PRAGMA foreign_key_check` before `COMMIT` and rolls back if any row is reported. After the transaction it restores the setting it found. `legacy_alter_table` must be off (the default), so the rename keeps the other tables' references.

### 9. The directory

```
migrations/
  velox.json
  velox.sum
  schema.json
  0001_create_users.sql
  0002_add_users_email.sql
  0003_add_users_email_online.sql
```

**`velox.json`** fixes the directory's dialect and settings. One directory serves one dialect.
```json
{"version": 1, "dialect": "postgres", "table": "velox_migrations", "lock_timeout": "5s"}
```
`table` and `lock_timeout` are optional, with these defaults. `diff` and `baseline` create the file when the directory does not exist and `-dialect` is given.

**SQL files.**
- **Naming:** `<version>_<name>.sql`. The version is a decimal of at least four digits; `diff` writes the last version plus one, zero-padded to four. The name is `[a-z0-9_]+`.
- **Ordering:** by version, numerically. Two files with one version are an error.
- **The default name (call)** comes from the first change (`create_users`, `add_users_email`, `drop_posts_legacy`), cut to 40 bytes. `-name` overrides it.
- **The header:** a file `diff` writes starts with `-- Generated by velox-gen <version> migrate diff. Review before applying; velox.sum checks it.` It is not a "DO NOT EDIT" header: until a file is applied, its author may add to it (a data backfill, say), then run `migrate hash`.

**Directives** are comment lines of the form `-- velox:<word> [args]`, before the first statement:
- `no-transaction`: the file runs statement by statement (§10). Needed for `CONCURRENTLY` and `ALTER TYPE … ADD VALUE`.
- `foreign-keys off`: SQLite only (§8.4).
- `lock-timeout <duration>`: §8.3.
- `allow <code> [<target>]`: records an allowed destructive change. Lint reads it.

An unknown directive, or a directive after a statement, is an error for `lint`, `diff` and the runner.

**Statements** are split at `;` outside quotes (`'…'`, `"…"`, `` `…` ``), comments (`--`, `/* */`) and PostgreSQL dollar quotes (`$tag$…$tag$`). MySQL's `DELIMITER` is not supported; procedures and triggers are out of scope. A fuzz test covers the splitter.

**`velox.sum`** holds the directory's hash and one line per file. Every SQL file is covered, and so are `schema.json` and `velox.json` **(changed: the decision named only the SQL files; the snapshot steers the next plan and the config fixes the dialect, so an edit to either must be caught too)**:
```
h1:<base64 of SHA-256 over the lines below>
0001_create_users.sql h1:<base64 of SHA-256 of the file>
…
schema.json h1:…
velox.json h1:…
```
- **CRLF:** a file's hash is taken over its bytes with CRLF turned into LF (call), so a Windows checkout does not change it.
- **Detection:** an edited, reordered, added or removed file makes `velox.sum` stale. `lint`, `hash -check`, `diff` and the runner refuse a stale sum until `migrate hash` rewrites it.
- **Merges:** two branches that each add a migration both change the first line, so git reports a conflict, and the second author re-runs `diff`.

**`schema.json`** is the snapshot: the model after the last file, as §2 says. `diff` writes it with every new file. A directory with no files has none, and its snapshot is the empty schema of its dialect.

**The history is linear (call).** Versions only grow. A pending file below the highest applied version is refused by the runner.

### 10. The runner

`Up(ctx, db *sql.DB, dir fs.FS, opts ...Option) (*Report, error)` applies the pending files. `velox-gen migrate apply` calls the same code.

**(changed: decision 5 had `Up(ctx, *sql.DB or velox DB, dialect, fs.FS)`.)**
- The dialect comes from `velox.json`, so it cannot disagree with the files.
- The runner takes a `*sql.DB` only, because the lock and the dirty state need one session, and a `velox.DB` exposes no connection. A pgx pool user passes `stdlib.OpenDBFromPool(pool)`.
- DDL does not belong in velox's pipeline: hooks, policies and tenants have no meaning for it.

**Steps.**
1. Read and check the directory: `velox.json`, `velox.sum`, every file, and the directives.
2. Take one connection (`db.Conn`). Check that it speaks the dialect and meets the minimum version: `server_version_num`, `@@version` or `sqlite_version()`.
3. Lock:
   - **PostgreSQL:** `pg_advisory_lock`, with a key fixed from the history table's name. Advisory locks are per database.
   - **MySQL:** `GET_LOCK(CONCAT('velox_migrate:', DATABASE(), ':', <table>), <wait>)`. The name holds the database because `GET_LOCK` is server-wide.
   - **SQLite:** each file runs in `BEGIN IMMEDIATE`, and the history is read again inside it, so two runners serialise per file and the second skips what the first applied.
   - The wait is bounded by `WithLockWait` (CLI `-lock-wait`, default 5m) and by `ctx`. A timeout is `ErrLockWait`.
4. Create the history table if it is missing.
5. Read the history. Then check, refusing on any failure:
   - every applied version is a file of the directory, with the same checksum (`*ChecksumError`);
   - no version is dirty (`*DirtyError`), unless `WithResume`;
   - the applied versions are a prefix of the files, or the files a prefix of the applied versions. A database ahead of the directory (an older build during a rolling deploy) applies nothing and is not an error: `Report.Ahead` is true. A gap or an out-of-order file is an error.
6. Apply each pending file up to `WithTarget(version)`.
7. Unlock, and release the connection.

**The history table** (`velox_migrations` unless `velox.json` says otherwise), in the connection's default schema:

| Column | PostgreSQL / MySQL / SQLite type | Meaning |
|---|---|---|
| `version` | `bigint` / `bigint` / `integer`, primary key | the file's version |
| `name` | `text` / `varchar(255)` / `text` | its name |
| `checksum` | `text` / `varchar(64)` / `text` | its `h1:` hash |
| `applied_at` | `timestamp with time zone` / `datetime(6)` / `datetime` | when it finished, or started if dirty |
| `duration_ms` | `bigint` | how long it ran |
| `dirty` | `boolean` / `tinyint(1)` / `boolean` | it stopped part-way |
| `statements` | `integer` | the statements applied, for a file run statement by statement |
| `error` | `text` | the failure that left it dirty, or "" |

The runner binds with each dialect's placeholders (`$1`, `?`). It reads `applied_at` as text, so the MySQL DSN needs no `parseTime` for migrating.

**Transactions.**
- **A file in a transaction** (PostgreSQL and SQLite, without `no-transaction`):
  1. `BEGIN` (`BEGIN IMMEDIATE` on SQLite);
  2. the lock timeout;
  3. the statements;
  4. on SQLite with `foreign-keys off`, `PRAGMA foreign_key_check`;
  5. the history row, `dirty = false`;
  6. `COMMIT`.

  A failure rolls everything back, so a file is applied wholly or not at all, and the version is never dirty.
- **A file statement by statement** (every MySQL file, since MySQL commits DDL implicitly, and any file with `no-transaction`):
  1. insert the history row with `dirty = true, statements = 0`;
  2. run each statement, and after each set `statements` to the count applied;
  3. on success, set `dirty = false` and the duration;
  4. on failure, record `error`, leave the row dirty, and stop the run with a `*DirtyError` naming the version, the statement number and the driver's error.

  InnoDB's DDL is atomic per statement (MySQL 8.0), so the recorded count is exact. On MySQL, a hand-written file wanting atomic DML writes its own `START TRANSACTION … COMMIT`.

**A dirty version stops every later run** until a human resolves it. `status` shows it with its statement count and error. There are two ways out:
- **`apply -resume`** (`WithResume`) continues the dirty version from its first unapplied statement. It is allowed only while the file's checksum is unchanged. This fixes a transient failure, such as a lock timeout.
- **`resolve -version N -applied`** marks the version applied, when a human finished it by hand. **`resolve -version N -undone`** deletes the row, when a human reverted its applied statements; the file may then be edited and run again.

**(changed: decision 5 listed no command to resolve a dirty version; "refuses to continue until a human resolves it" needs one, so the runner gains `Resolve`, `WithResume` and the `resolve` subcommand.)**

**Baseline versions.** `WithBaseline(version)` (CLI `apply -baseline N`) records the files up to `version` as applied without running them. It is allowed only when the history is empty. That is how an existing database adopts a baselined directory (§12).

**`Status`** reports the same reading without locking or applying. **`Verify(ctx, db, dir)`** is the test helper of decision 2. It applies the directory to an empty database, inspects the snapshot's tables, and fails unless they equal `schema.json`. An application calls it in its own tests, on SQLite or a scratch PostgreSQL, to catch a hand edit that the snapshot does not know.

### 11. Inspect and drift

`Inspect(ctx, db *sql.DB, d velox.Dialect, tables []TableRef) (*Schema, error)` reads the named tables. `nil` means every table in the connection's default schema. The history table is always left out. A named table that does not exist is absent from the result, not an error.

- **PostgreSQL:** `pg_catalog`.
  - Column types come from `format_type`, which gives §4's spellings.
  - Defaults come from `pg_get_expr`; identity from `attidentity`.
  - Indexes, with their predicates, come from `pg_index`/`pg_get_expr`; constraints from `pg_constraint`/`pg_get_constraintdef`.
  - Comments come from `obj_description`/`col_description`; enum types from `pg_enum`.
  - The schema `""` stands for `current_schema()`.
- **MySQL:** `information_schema`.
  - `COLUMNS.COLUMN_TYPE` and `EXTRA` (`auto_increment`, `DEFAULT_GENERATED`); `STATISTICS`; `TABLE_CONSTRAINTS`, `KEY_COLUMN_USAGE`, `REFERENTIAL_CONSTRAINTS` and `CHECK_CONSTRAINTS`.
  - `TABLES.TABLE_COLLATION` and `ENGINE`. A table that is not InnoDB is reported by drift.
  - The schema `""` stands for `DATABASE()`.
- **SQLite:** `pragma table_xinfo`, `index_list`, `index_info` and `foreign_key_list`. The pragmas do not give constraint names or `CHECK` text, so `Inspect` also parses the table's `CREATE TABLE` in `sqlite_schema` (velox's own shape and the common hand-written forms). Where it cannot parse one, names are "" and those constraints are compared by definition (call).

**Canonical checks.** An enum check is recognised in each dialect's printed form and rewritten into the model's: PostgreSQL's `((c = ANY (ARRAY['a'::text, 'b'::text])))`, MySQL's ``(`c` in (_utf8mb4'a',_utf8mb4'b'))``, SQLite's text verbatim. Any other check keeps the database's text. Partial-index predicates are compared after white space, outer parentheses and identifier quoting are normalised. `RESTRICT` and `NO ACTION` are one action on MySQL.

**Objects the model did not create.** An index, check or foreign key on a known table is modelled, so a baselined database's next `diff` proposes dropping it, as a review change the author sees. An unknown table is never read, dropped or reported (decision 3).

**ent-created databases (ruling 21).** ent maps an enum to `character varying` with no check on PostgreSQL, to a native `enum(…)` on MySQL, and to `text` on SQLite. `Inspect` reports these as they are: a `character varying` column with no check, or a column of type `enum('a','b')`. It does not misread them as velox's shape. Drift reports the difference ("type character varying, no check; the schema wants text with users_role_check"). After `baseline`, the next `diff` plans the change: `alter-type` and `add-check` for the default shape, or nothing for a MySQL field declared `Native()` with the same values.

**Drift** (`velox-gen migrate drift`) inspects the snapshot's tables and compares the result with `schema.json`, reporting each difference as the change that would remove it. **(changed: decision 3 restricted drift to "the tables the snapshot or schema names" and compared with the schema. The snapshot is what the applied directory should have produced. A schema ahead of the snapshot is `diff -check`'s finding, not drift.)** Drift needs the database at the directory's last version, because only the last snapshot exists. A database behind it is an error naming the pending files.

### 12. Baseline

`velox-gen migrate baseline -dialect d -db DSN [package]` adopts an existing database into a new, empty directory:
1. It inspects the tables the schema package names, join tables included.
2. It writes `schema.json` from that inspection.
3. It writes `0001_baseline.sql`, holding the `CREATE` statements of that snapshot. A fresh database (a new environment, a test) can then be built from the directory.
4. It writes `velox.json` and `velox.sum`.

Baseline only reads the database. Each existing environment then runs `apply -baseline 1` once, which records 0001 as applied without running it. The next `diff` brings the database to the schema, with every destructive change gated as usual.

**(changed: decision 3 had baseline write "a first empty migration recorded as applied". An empty first file cannot build a fresh database, and recording from baseline adopts only the one database it read. The DDL file plus `apply -baseline` serves every environment the same way.)**

### 13. The CLI

```
velox-gen migrate diff     [-dir ./migrations] [-dialect d] [-name n] [-allow code[=target],...]
                           [-rename-table old=new]... [-rename-column table.old=new]...
                           [-lock-timeout 5s] [-check] [-dry-run] [package]
velox-gen migrate apply    [-dir ./migrations] [-db dsn] [-to version] [-baseline version]
                           [-resume] [-lock-wait 5m] [-dry-run]
velox-gen migrate status   [-dir ./migrations] [-db dsn] [-json]
velox-gen migrate drift    [-dir ./migrations] [-db dsn] [-json]
velox-gen migrate baseline [-dir ./migrations] -dialect d [-db dsn] [package]
velox-gen migrate lint     [-dir ./migrations] [-since version]
velox-gen migrate hash     [-dir ./migrations] [-check]
velox-gen migrate resolve  [-dir ./migrations] [-db dsn] -version n (-applied | -undone)
```

- **The package** is the schema package, `./schema` by default, as for `generate`. Flags may follow it, as elsewhere in velox-gen.
- **`-db`** is the driver's DSN for the directory's dialect: a pgx connection string, a go-sql-driver DSN, or a SQLite path or URI. When it is empty, `$VELOX_DB` is read, which keeps a password out of shell history. velox-gen links the three drivers already in the root module.
- **diff** loads the schema, builds the model for the directory's dialect, plans against the snapshot, and writes the new file or files, `schema.json` and `velox.sum`.
  - `-rename-table` and `-rename-column` are repeatable. A table may be qualified, `billing.invoices`; for a column the last dot splits the column off. **(changed: decision 8 wrote `-rename users.name=full_name` for both; two flags make a table rename and a column rename impossible to confuse.)**
  - No change prints `no changes` and writes nothing.
  - `-dry-run` prints the files instead of writing them.
  - `-check` writes nothing and exits 3 when the schema differs from the snapshot or `velox.sum` is stale. CI runs it.
- **apply** applies the pending files (§10). `-dry-run` prints them. `-to` stops at a version.
- **status** prints applied, pending, dirty and ahead versions.
- **drift** prints the differences (§11).
- **lint** checks every file, or those from `-since`:
  - the directives;
  - the statement split;
  - `CONCURRENTLY` or `ALTER TYPE … ADD VALUE` only in a `no-transaction` file;
  - no `BEGIN`/`COMMIT` in a PostgreSQL or SQLite file run in a transaction.

  It also classifies statements it can parse (`DROP TABLE`, `DROP COLUMN`, `ALTER … TYPE`, `MODIFY COLUMN`, `SET NOT NULL`, `TRUNCATE`, and `DELETE` or `UPDATE` without `WHERE`), reporting a destructive one that no `allow` directive covers. It cannot see everything a hand-written file does; the main gate is `diff`.
- **hash** rewrites `velox.sum`; with `-check` it exits 3 when the sum is stale.
- **resolve** is §10's.

**Exit codes**, as velox-gen's:

| Code | Meaning |
|---|---|
| 0 | success; `diff` with no changes; `status` up to date or ahead; `drift` with none |
| 1 | an error: a refusal (blocked destructive changes, a schema the dialect cannot hold), a database error, a dirty version, a changed applied file, a stale sum where a fresh one is required, lint findings that block |
| 2 | misuse: an unknown subcommand or flag, a malformed `-allow` or `-rename-*`, `-dialect` disagreeing with `velox.json` |
| 3 | stale or drift: `diff -check` and `hash -check` find the directory stale; `status` finds pending files; `drift` finds differences |

### 15. DSL additions and generator fixes

#### 15.1 `field.SchemaDefault` and `Native`

```go
func (c common[B]) SchemaDefault(m map[string]string) B
func (b *EnumBuilder) Native() *EnumBuilder
func (b *EnumOfBuilder[T]) Native() *EnumOfBuilder[T]
```

**`SchemaDefault`** gives the database default per dialect, as SQL, such as `{field.Postgres: "now()", field.MySQL: "CURRENT_TIMESTAMP(6)", field.SQLite: "CURRENT_TIMESTAMP"}`.
- Its keys are validated like `SchemaType`'s; an unknown key is a misuse.
- It reaches the load model as `loadjson.Field.SchemaDefault`; `loadjson.Version` becomes 3.
- It does not reach the plugin model.
- It changes no generated Go: velox's inserts send every column (§5).
- A tenant field refuses it (rule 16 extended), as does an integer ID, whose value is an identity (rule 21 extended).

**`Native()`** makes an enum a native enum on PostgreSQL and MySQL (ruling 21). On SQLite it changes nothing. Why one option and not one per dialect: one schema works on all three dialects, SQLite has no native enum to choose, and per-dialect column types are `SchemaType`'s job already. The name says what it does without naming a dialect. The load model gains `loadjson.Field.Native`.

#### 15.2 Name rules

- **Rule 44, extended (closes follow-up :271).** It runs on the capped names, over the whole namespace of §6. It reports two elements, which may be in two schemas.
- **Rule 50 (new).** An explicit identifier over 63 bytes is refused: a table (`schema.Table`), a column (`StorageKey`), a join table or its columns (`edge.Table`, `edge.Columns`), an index `StorageKey`, or a `Symbol`.
- **Rule 51 (new).** A relation that is not many-to-many takes one `Symbol`, and a many-to-many one two (`Symbols`). When both edges of a pair give symbols, they must agree, as rule 47 asks of `OnDelete`. velox2 is the first to use the symbols (follow-up :131).
- **The cap** (§6) is applied in `indexName` and in the other derived names, in one function in `internal/gen` that `Build` and `Tables` share.

#### 15.3 Nullability (closes follow-up :303)

The plugin's `Nullable` says yes for an `Optional` JSON field of an interface, func or chan type, and `ColumnDesc` refuses `Nullable` on such a field.

- **The interface kind cannot occur.** `field.JSON(name, typ)` takes the Go type from `reflect.TypeOf(typ)`, which is never an interface.
- **func, chan, complex and `unsafe.Pointer` cannot be encoded.** `encoding/json` refuses them, so every write would fail.

**Rule 49 (new)** therefore refuses a JSON field whose Go type is of any of these kinds, unless the type has its own JSON or text encoding (`GoType.Marshaler`). With those kinds gone, the plugin's rule and the core's agree for every kind that is left (slice, map, pointer, and struct and scalar types through rule 48). `Tables` uses that one rule. **(changed: decision 14 preferred accepting such a field, the plugin rule's answer. Accepting it would make the core take `Nullable` on a field that no codec can write. Refusing removes the mismatch, and loses nothing a program could use.)**

#### 15.4 MySQL `Index.Where`

velox-gen's `Build` does not know the dialect. The schema is dialect-free, and one schema may serve several directories. So the refusal is `Tables`'s, at plan time for a MySQL directory, with the index's file:line (§3). **(changed: listed among the generator fixes, but the generator cannot make it.)**

#### 15.5 `SQLType` leaves the core (call)

`ColumnDesc.SQLType` and `ColumnInfo.SQLType` hold one string for every dialect, nothing fills them, and nothing reads them. The planner owns SQL types. Both fields are removed before 1.0. Generated code never set them, so `GeneratedCodeIsVersion4` stays.

#### 15.6 `mixin.Time`

`mixin.Time` gains its `SchemaDefault`s (§5).

### 16. Errors

Every refusal names the schema's file:line when the element has one, in velox-gen's format, with paths relative to the working directory:

```
schema/user.go:14: schema User: index 0: MySQL has no partial indexes (Where); drop Where or use a separate MySQL schema
schema/user.go:9: schema User: field "email": index users_email_unique is also schema Account's index 2 (rule 44)
```

`diff` refusing destructive changes lists each with its code and the flag that allows it. A dropped element has no position in the schema, so it is named by table and column:

```
velox-gen: migrate diff: 2 destructive changes refused:
  users.legacy: drop-column: drops column legacy and its data; allow with -allow drop-column=users.legacy
  schema/user.go:12: users.nickname: set-not-null: fails if a row holds NULL; allow with -allow set-not-null=users.nickname
```

The runner's errors name the file and, for a statement-by-statement file, the statement:

```
migrate: 0004_add_users_org_id.sql: statement 2 of 3: Error 1205: Lock wait timeout exceeded
  version 4 is dirty; fix the cause and run migrate apply -resume, or undo statement 1 and run migrate resolve -version 4 -undone
migrate: 0002_create_posts.sql was applied with checksum h1:AbC… and is now h1:XyZ…
migrations/velox.sum is out of date; run velox-gen migrate hash if the edits are intended
```

A rename flag naming nothing says where it looked: `-rename-column users.nme=full_name: table users in schema.json has no column nme`.

### 17. Testing

- **Generator.**
  - Rule tests for 44 (extended), 49, 50 and 51, and for `SchemaDefault`'s misuses.
  - A table test of the cap: names of 62, 63 and 64 bytes, and multi-byte names cut at a rune boundary.
  - `Tables` goldens: one schema covering every field type, option and relation kind, as `schema.json` per dialect.
  - Each plan-time refusal, with its position.
- **Render goldens.** For each change kind and dialect, `migrate/testdata/render/<case>.<dialect>.sql`, rewritten with `-update`. They include the SQLite rebuild, the PostgreSQL online script, `NOT VALID`/`VALIDATE`, the enum swap, and MySQL's `MODIFY` around a key's type change. Lint has goldens of its findings, and the directory of its files and `velox.sum`.
- **Model invariants without a database.**
  - `Diff(x, x)` is empty.
  - Applying `Diff(a, b)` to `a` with an internal model-level `apply` gives `b`.
  - No function writes through its arguments (deep copies compared).
  - Output is the same twice.
- **Fuzz.** The statement splitter (`FuzzSplit`) and the literal renderer (`FuzzLiteral`, round-tripped through each dialect's normaliser).
- **Real-database itests** on PostgreSQL 16, MySQL 8.4 and SQLite, for every change kind. Each starts from a fresh database: a schema on PostgreSQL, a database through `VELOX_TEST_MYSQL_ADMIN` on MySQL, a file in `t.TempDir()` on SQLite. After each apply, three invariants hold:
  1. `Inspect` equals the model;
  2. a second `Diff(snapshot, model)` is empty;
  3. drift, `Diff(Inspect, snapshot)`, is empty.
- **Binding.** For each type of §4, a row round-trips through velox on each dialect and both PostgreSQL executors. This covers `uint64` at 2⁶³−1 and at 2⁶⁴−1 (which SQLite must refuse), the test-local UUID type, and JSON NULL against `null`.
- **The runner.**
  - Two concurrent `Up`s apply each file once (PostgreSQL, MySQL, SQLite on a file).
  - A MySQL file failing at statement 2 is dirty. `apply` refuses it, `-resume` finishes it after the cause is removed, and `resolve -undone` clears it.
  - An edited applied file is refused.
  - A database ahead of the directory applies nothing.
  - `apply -baseline` refuses a non-empty history.
  - A SQLite rebuild of a parent with `ON DELETE CASCADE` children keeps the children, and keeps the `AUTOINCREMENT` counter.
- **Property test.** Random schema evolutions, applied in sequence on SQLite always and on PostgreSQL and MySQL when their variables are set.
  - Each step adds or drops a table, adds, drops, renames (by flag) or retypes a column along the widening lattice, toggles nullability, changes a default, an index, a unique, a foreign key, an enum's values or a comment, with every destructive code allowed.
  - Rows inserted before each step are checked after it: renamed and rebuilt columns keep their values.
  - All three invariants hold after every step.
  - The seed is logged, and `-seed` replays it. It runs 8 seeds of 40 steps by default and fewer under `-short`, within the machine's memory.
- **The CLI.** `cmd/velox-gen` tests run every subcommand on SQLite, with their exit codes, as `cli_test.go` does.
- **Moving onto the planner (decision 16).**
  - The examples drop their hand-written DDL for an embedded `migrations/` directory and `migrate.Up`.
  - `internal/testmodel` gets `migrations/{postgres,mysql,sqlite}`, and the itests that use its tables create them through the planner.
  - Itests that test a constraint's hand-written name keep their DDL.
  - CI runs `velox-gen migrate diff -check` on each of these directories, and the new itests, in `ci.yml` and `scripts/ci-local.sh` alike.

## Rulings

1. **Own planner, no Atlas** (decision 1). Three dialects and one model are small enough to own, and they keep the dependency discipline, deterministic output and the safety rules in velox's hands. If wrong, it costs more code to own.
2. **Versioned SQL files are the product; no auto-migrate for production** (decision 2). §9.
3. **Planning reads the snapshot, never the database** (decision 3). The database is read only by `drift`, `baseline` and the runner.
4. **One model, one builder** (decision 4): `internal/gen.Tables`, values never mutated, `Pos` neither serialized nor compared. The model gains `Pos`, `Collation`, `Enums`, `Check.Expr` and `TableRef` (changed, §2).
5. **`migrate` is public and imports the root package for `velox.Dialect`; not a plugin** (§1).
6. **`Up` takes a `*sql.DB`, and the dialect comes from `velox.json`** (changed, §10).
7. **The CLI is `velox-gen migrate`, with `resolve` added** (changed, §10, §13); `-rename-table` and `-rename-column` replace one `-rename` (changed, §13).
8. **Locks:** PostgreSQL advisory lock, MySQL `GET_LOCK` named with the database, SQLite `BEGIN IMMEDIATE` per file with the history read again inside it (§10).
9. **Transactions:** one per file on PostgreSQL and SQLite. Statement by statement on MySQL and for `no-transaction` files, with a dirty row, a statement count, `-resume` and `resolve` (§10).
10. **SQLite's `foreign_keys` is turned off around the transaction, and `foreign_key_check` runs before `COMMIT`** (changed, §8.4).
11. **The lock timeout is a directive the runner applies,** 5s by default, on PostgreSQL and MySQL (changed, §8.3).
12. **Lint classes and codes as in §8.1;** `-allow code[=target]` extends the defaults, and each allowance is written into the file (decision 7).
13. **The PostgreSQL online script:** `CONCURRENTLY` indexes, each with its `DROP … IF EXISTS`, `VALIDATE CONSTRAINT`, and `SET NOT NULL` through a validated check (§8.3).
14. **Renames:** tables and columns only by flag (decision 8). Indexes and constraints are matched by definition, so they need none (changed, §6, §7.1).
15. **Types as in §4,** spelled as each database reports them. `SchemaType` wins and is normalised by an alias list.
16. **`uint`/`uint64` is `numeric(20,0)` on PostgreSQL, but an integer ID is always an identity, `bigint` for `uint64`; a foreign-key column copies the referenced column's type** (§3, §4).
17. **SQLite IDs are `integer PRIMARY KEY AUTOINCREMENT`** (changed, §4).
18. **MySQL:** `tinyint(1)` for bool (changed, §4), strings and blobs sized by bytes, `utf8mb4_bin` tables, `Table.Collation` (§4).
19. **UUIDs are the canonical text;** a byte-binding `Valuer` needs `SchemaType` (§4).
20. **Enums are text or `varchar(255)` with a named `CHECK` on every dialect, by default** (decision 10). On MySQL adding a check copies the table, which `add-check` says.
21. **Native enums, opt-in (the controller's refinement of decision 10):** `field.Enum(…).Native()`.
    - **PostgreSQL:** a named type, `<table>_<col>` (capped, and in rule 44's namespace). Adding a value is `ALTER TYPE … ADD VALUE [BEFORE …]`, in its own file outside a transaction. A removal or reorder is destructive (`drop-enum-value`, `reorder-enum`), rendered as the type swap.
    - **MySQL:** `enum(…)`. A value added at the end is a `MODIFY COLUMN` and safe. A removal, a reorder or an insertion elsewhere is destructive. The doc of `Native` says that MySQL sorts an `ENUM` by its index, not its text.
    - **SQLite:** keeps the `CHECK`.
    - **Baseline and drift recognise an ent-created database:** a PostgreSQL `character varying` with no check, and a MySQL native `enum`. They report the difference rather than misreading it (§11).
    - **The name:** one option, not one per dialect. One schema serves every dialect, SQLite has no choice to make, and per-dialect types are `SchemaType`'s already.
22. **Defaults:** a literal `Default` becomes the database default; `SchemaDefault` gives expressions; an `Optional` value field of string, bool or number defaults to its zero value (changed, §5). JSON, bytes, other, func, time and UUID defaults stay Go-side. There is no `ON UPDATE`.
23. **`mixin.Time` gains `SchemaDefault`s** (§5, §15.6).
24. **Names:** one 63-byte cap with an FNV-1a suffix on derived names. Explicit names over 63 bytes are refused by rule 50 (changed, §6). Rule 44 covers one case-insensitive namespace per schema.
25. **Foreign keys are named `<table>_<col>_fkey`, or by `Symbol`;** rule 51 checks the symbols (§15.2).
26. **Every foreign-key column is indexed** unless an index or the primary key leads with it (§3).
27. **Join tables:** primary key (owner, target), an index on the target, both foreign keys `ON DELETE CASCADE` (§3).
28. **Unique fields and indexes are unique indexes, not constraints** (§8.2).
29. **Nullability:** rule 49 refuses JSON fields of unencodable kinds, so one rule holds for the plugin, the core and the planner (changed, §15.3).
30. **MySQL `Where` and the other dialect limits are refused at plan time by `Tables`, with file:line** (changed for `Where`, §3, §15.4).
31. **Diff's order is §7.3's.** A primary-key change is refused.
32. **The directory:** `NNNN_name.sql`, the directives of §9, `velox.sum` over the SQL files, `schema.json` and `velox.json`, hashed with CRLF as LF (changed, §9), and a default name from the first change.
33. **The history is linear.** A database ahead of the directory is not an error; a gap is (§10).
34. **Drift compares the database with the snapshot, at the directory's last version** (changed, §11).
35. **Baseline writes the inspected DDL and only reads the database; `apply -baseline` records it** (changed, §12).
36. **`Inspect` models the objects it finds on known tables, ignores unknown tables, and parses SQLite's `CREATE TABLE` for names and checks** (§11).
37. **PostgreSQL schemas are created `IF NOT EXISTS`; MySQL databases must exist; SQLite refuses schemas** (§3, §8.2).
38. **The statement splitter** knows quotes, comments and dollar quotes, and not `DELIMITER` (§9).
39. **`Verify` is the test helper** (§10).
40. **`ColumnDesc.SQLType` and `ColumnInfo.SQLType` are removed** (§15.5).
41. **Minimum versions:** PostgreSQL 12 (`SET NOT NULL` from a valid check), MySQL 8.0.16 (enforced `CHECK`), SQLite 3.35 (`DROP COLUMN`).
42. **Out of scope as decision 15 lists,** and data migrations are hand-written files.
43. **Tests as §17** (decision 16).
44. **Three plans, re-cut** (changed, Plans).
